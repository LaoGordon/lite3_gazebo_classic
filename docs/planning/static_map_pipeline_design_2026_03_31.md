# 静态 `/map` 链路设计草案（2026-03-31）

本文档用于梳理 Lite3 Gazebo Classic 当前导航系统从“最小闭环”走向“真正全局导航”所需的静态 `/map` 链路设计。

当前系统已经具备：

- FAST-LIVO2 输出里程计与点云
- `fastlivo_nav_bridge` 将其整理为导航接口
- `floor_mapper` 生成局部滚动 2D 栅格
- Nav2 最小闭环已经跑通

但当前仍然缺少真正的全局静态地图来源，因此 `global_costmap` 目前只能处于过渡配置。要支撑更远距离规划、拐角路径、长走廊和后续多楼层扩展，就必须建立一条独立、稳定的 `/map` 链路。

## 一、设计目标

该链路需要解决四个问题：

1. 如何从当前感知系统中获得可落盘的全局环境表达
2. 如何把全局 3D 表达转换为 2D 静态导航地图
3. 如何把这张静态地图以 `/map` 的形式提供给 Nav2
4. 如何让当前基于 FAST-LIVO2 的定位结果与真正的 `/map` 语义闭合

## 二、当前系统中的角色边界

在新架构下，应明确区分以下三类数据：

### 1. 局部动态输入

当前的 `floor_mapper` 输出 `/floor_map`。

它的职责应继续保持为：

- 机器人周围局部区域的 2D 障碍投影
- 给 `local_costmap` 或局部导航层提供动态环境输入
- 不承担全局地图职责

### 2. 全局静态地图

后续新增的 `/map` 应承担：

- 提供长期稳定的全局平面占据栅格
- 给 `global_costmap` 提供静态规划蓝图
- 作为楼层地图、多楼层切换与任务规划的基础数据

### 3. 位姿与 frame 对齐层

当前 `fastlivo_nav_bridge` 使用的是：

- FAST-LIVO2 原始 `camera_init` 语义
- bridge 重映射为 `odom` 和 `map`
- `map -> odom` 当前近似为恒等

在真正引入静态 `/map` 后，`map` 不再只是一个临时标签，而是要对应到真实全局地图参考系。因此，定位层与地图层之间的 frame 关系必须重新定义。

## 三、推荐的数据流

推荐采用如下分层数据流：

`FAST-LIVO2 -> 全局点云落盘 -> 离线 2D 投影/切片 -> 静态地图文件 (.pgm + .yaml) -> map_server -> /map -> global_costmap`

同时保留现有局部链路：

`FAST-LIVO2 -> fastlivo_nav_bridge -> /obstacle_points -> floor_mapper -> /floor_map -> local_costmap`

这样做的好处是：

- 全局层和局部层职责清晰
- `floor_mapper` 不再被误用为全局地图来源
- 后续多楼层架构可以直接围绕静态地图文件组织
- 局部动态障碍与全局静态结构不会混杂在一个模块里

## 四、最小可落地版本

建议先做一个最小可用版本，而不是一开始就追求完整自动化。

### 第一步：全局点云落盘

目标：把 FAST-LIVO2 运行一段时间后的全局 3D 环境保存下来。

推荐思路：

- 在仿真中让机器人完成一段覆盖主要通行区域的运动
- 从 FAST-LIVO2 当前稳定可用的全局点云输出中导出一份全局 PCD
- 将该 PCD 作为静态地图制备的原始输入

这里的关键不是立即自动化，而是先确认：

- 导出的点云范围是否覆盖目标楼层
- 点云密度是否足以支撑 2D 栅格生成
- 点云 frame 是否与当前全局定位语义一致

### 第二步：离线 2D 切片与投影

目标：把全局 3D 点云转换为一张可被 Nav2 使用的静态 2D 地图。

推荐离线处理逻辑：

- 对全局 PCD 做高度裁剪
- 仅保留导航关心的障碍高度范围
- 对地面与低矮噪声做过滤
- 将点投影到二维平面
- 以固定分辨率生成 OccupancyGrid
- 输出 `.pgm` 与 `.yaml`

建议将此步骤视为一个独立离线工具，而不是塞进 `floor_mapper`。

原因是：

- `floor_mapper` 当前是在线局部模块
- 全局地图制备是离线或半离线流程
- 两者的输入范围、时效性和目标都不同

### 第三步：引入 `map_server`

目标：让 Nav2 获得标准 `/map` 输入。

推荐做法：

- 在 `quadruped_nav_bringup` 中新增一个专门的静态地图 launch
- 启动 `nav2_map_server`
- 使用上一步生成的 `.yaml` 地图文件
- 由 `map_server` 发布 `/map`

在这一阶段，`global_costmap` 可以恢复为标准结构：

- `StaticLayer`
- `map_topic: /map`

### 第四步：重定义 `map -> odom`

这是静态地图链真正接入后最关键的一步。

当前 `map -> odom` 是桥接层发布的恒等变换，只适用于“最小闭环临时语义”。

一旦引入真正 `/map`，就必须重新明确：

- `odom` 是否继续表示 FAST-LIVO2 的连续局部参考系
- `map` 是否表示静态全局地图参考系
- 谁来提供 `map -> odom`

这是整个链路里最不能模糊的一步。

## 五、关于 `map -> odom` 的建议

当前不建议继续长期使用 bridge 内的恒等 `map -> odom`。

进入静态地图阶段后，建议把语义收严为：

- `odom`：连续、局部、适合控制与短时运动的参考系
- `map`：静态全局地图参考系

然后在两类实现中做选择：

### 方案 A：增加外部定位/对齐层

由单独模块负责把 FAST-LIVO2 当前位姿与静态地图对齐，发布真实 `map -> odom`。

优点：

- 模块职责清晰
- bridge 不需要承担地图级对齐逻辑
- 未来更容易扩展到多楼层地图切换

缺点：

- 需要新增一层定位或地图配准能力

### 方案 B：让 bridge 承担部分显式 TF 变换职责

bridge 不再仅做 frame 重命名，而是显式处理 FAST-LIVO2 frame 到导航 frame 的变换。

优点：

- 可以减少中间环节

缺点：

- bridge 职责会显著膨胀
- 一旦后续引入多楼层、重定位或地图切换，bridge 很容易变成职责混杂的模块

当前更推荐方案 A，即把 `/map` 对齐视为独立定位问题，而不是直接塞进 bridge。

## 六、建议新增的文件与入口

在当前仓库结构下，建议新增如下内容：

### 1. 文档层

- 一份静态地图制备说明文档
- 一份地图文件目录约定文档

### 2. `quadruped_nav_bringup` 层

建议新增：

- 一个专门负责 `map_server` 的 launch 文件
- 一个用于切换“最小闭环模式 / 静态地图模式”的 launch 参数

例如：

- `enable_static_map:=true|false`
- `map_yaml:=/abs/path/to/floor_1.yaml`

### 3. 地图资源目录

建议预留统一目录，例如：

- `navigation/quadruped_nav_bringup/maps/`

用于存放：

- `floor_1.yaml`
- `floor_1.pgm`
- 后续多楼层地图文件

## 七、对现有代码的影响边界

引入静态 `/map` 链路后，影响边界大致如下：

### 1. `floor_mapper`

- 短期无需重构
- 继续服务局部层
- 不再承担任何全局地图职责

### 2. `fastlivo_nav_bridge`

- 短期可继续保持当前实现
- 中期必须重新定义点云与 odom 的语义边界
- 不建议继续长期依赖“直接覆盖 frame_id”作为最终方案

### 3. `nav2_params.yaml`

后续将需要两套或两阶段配置：

- 当前过渡配置：无真正静态 `/map`
- 静态地图配置：`global_costmap` 恢复 `StaticLayer -> /map`

### 4. `navigation_main.launch.py`

建议保留现有主入口，但允许按参数选择是否启动静态地图链。

## 八、建议的实施顺序

建议按如下顺序推进：

1. 保持当前最小闭环继续可运行
2. 确认全局点云落盘来源与导出方式
3. 先做离线 2D 投影脚本或工具验证
4. 生成第一张可用的 `.pgm + .yaml`
5. 在 bringup 中接入 `map_server`
6. 将 `global_costmap` 切回标准 `/map` 静态层
7. 最后再收敛 `map -> odom` 的正式语义与实现

## 九、当前阶段结论

当前项目已经具备继续推进静态 `/map` 链路的基础条件，但不应跳步。

最务实的路线不是立即重写 bridge，也不是把 `floor_mapper` 强行扩展成全局建图器，而是：

- 保留现有最小闭环
- 新增独立静态地图制备链
- 让 `global_costmap` 回归标准 `/map` 输入
- 再在此基础上正式收敛 `map / odom / base` 语义

这条路线既能保护当前已跑通的最小链路，也能为后续多楼层与楼梯扩展保留清晰边界。
