本文档用于总结截至 2026 年 3 月 25 日，Lite3 Gazebo Classic 工作区中"建图、路径规划、导航"相关全链路已经解决了什么问题、已经验证了哪些能力，以及下一步计划是什么。

这里讨论的重点不是四足本体长期运动稳定性，而是导航系统本身是否已经形成一条完整可运行的链路。

## 一、当前已经解决了什么问题

### 1. 已经建立 FAST-LIVO2 到导航侧标准接口的适配层

当前系统已经不再直接让下游模块依赖 FAST-LIVO2 原始内部话题，而是通过 `fastlivo_nav_bridge` 做统一整理。

已经解决的问题包括：

- 将 FAST-LIVO2 的 `/aft_mapped_to_init` 整理为导航侧可消费的 `/odom`
- 建立 `map -> odom -> base` 的标准导航 TF 链
- 将 FAST-LIVO2 的 `/cloud_registered` 整理为 `/obstacle_points`

这意味着 FAST-LIVO2 已经成功从"算法输出"转换成"导航输入"。

### 2. 已经建立点云到 2D 导航地图的转换链路

当前 `floor_mapper` 已经不是占位骨架，而是具备第一版实际功能。

已经解决的问题包括：

- 订阅 `/obstacle_points`
- 结合 `/odom` 构建滚动窗口地图
- 对点云做高度裁剪
- 对点云做距离裁剪
- 对机器人近体点做自体剔除
- 投影生成 `OccupancyGrid`
- 发布 `/floor_map`

这意味着系统已经具备了"3D 感知输入 -> 2D 导航地图输入"的基础能力。

### 3. 已经把 Nav2 实际接入当前链路

当前 `quadruped_nav_bringup` 已经不只是启动 bridge 和 mapper，而是已经可以拉起完整 Nav2。

已经解决的问题包括：

- 补齐 Nav2 最小 bringup 入口
- 补齐当前四足导航链所需的参数文件
- 让 Nav2 消费：
  - `/odom`
  - `map -> odom -> base`
  - `/floor_map`
  - `/obstacle_points`

这意味着导航系统已经不再停留在"接口预留"阶段，而是已经形成了实际运行的规划与控制链。

### 4. 已经把导航输出真正接到底层运动接口

当前系统不仅能规划，还能把控制输出送到底层四足控制主接口。

已经解决的问题包括：

- `/navigate_to_pose` 可接受目标
- Nav2 控制器可输出 `/cmd_vel_nav`
- 底层主接口可继续输出 `/cmd_vel`
- 机器人在仿真中已经出现真实前进

这意味着系统已经从"能看到 topic"进入"能驱动机器人运动"的阶段。

## 二、当前已经验证了哪些能力

### 1. 已验证感知与建图输入链

已经实际验证：

- FAST-LIVO2 的 `/aft_mapped_to_init` 正常发布
- FAST-LIVO2 的 `/cloud_registered` 正常发布
- bridge 输出的 `/odom` 正常
- `floor_mapper` 输出的 `/floor_map` 正常

因此，当前已经验证系统具备：

- 实时位姿输入能力
- 实时障碍点云输入能力
- 实时 2D 导航地图生成能力

### 2. 已验证标准导航接口链

已经实际验证：

- `map -> odom -> base` TF 链存在
- `/odom`、`/floor_map`、`/obstacle_points` 都能被稳定发布

因此，当前已经验证系统具备：

- 标准 ROS 导航接口对接能力
- 给 RViz / Nav2 / costmap 提供统一输入的能力

### 3. 已验证 Nav2 生命周期与规划控制链

已经实际验证：

- `/planner_server`
- `/controller_server`
- `/bt_navigator`
- `/behavior_server`

以上核心 Nav2 节点都能进入 `active [3]`。

并且已经验证：

- `/navigate_to_pose` 目标可被接受
- action 可返回 `SUCCEEDED`

因此，当前已经验证系统具备：

- 基础路径规划能力
- 基础路径跟踪能力
- 基础导航任务执行能力

### 4. 已验证从目标到运动输出的完整闭环

已经实际验证：

- `/cmd_vel_nav` 有实际输出
- `/cmd_vel` 与 `/cmd_vel_nav` 对应
- 机器人在近距离和中短距离目标测试中实际发生前进

并且已经完成过：

- `0.3 m` 目标单次成功验证
- `0.3 m` 目标 5 次重复 action 成功验证
- `0.6 -> 0.0 -> 0.6` 多次往返目标成功验证

因此，当前已经验证系统具备：

- 目标点导航的最小闭环能力
- 短距离重复导航能力
- 全链路联调能力

## 三、当前系统已经具备的能力边界

截至 2026 年 3 月 25 日，可以认为当前系统已经具备以下能力：

1. FAST-LIVO2 输出可以作为导航定位与障碍输入来源
2. 点云可以被转换成 2D 导航地图
3. Nav2 可以基于当前输入运行
4. 系统可以接收导航目标并输出运动指令
5. 机器人已经能够在仿真中完成至少一种最小导航任务

换句话说，当前已经实现并验证了：

`FAST-LIVO2 -> 地图生成 -> 路径规划 -> 控制输出 -> 机器人运动`

这意味着"建图、路径规划、导航"这条主链路已经打通。

## 四、当前尚未解决的问题

以下问题目前仍然存在，但它们不改变"全链路已打通"的结论：

### 1. 运动稳定性不是当前链路验证的一部分

当前测试中出现过机器人侧翻。

这说明：

- 四足本体稳定性仍需后续处理
- `mode = 4` 下长时间运行策略仍需优化

但这属于运动稳定性问题，不是导航链路是否存在的问题。

### 2. 目标容差和重复性还需要继续收敛

当前 action 多次返回 `SUCCEEDED`，但仍需继续确认：

- 是否存在过早判定成功
- 更远距离目标下是否仍然稳定
- 多轮运行后地图、位姿和行为是否仍一致

### 3. 地图语义和 frame 语义还可继续收严

当前系统已经能工作，但从工程严谨性角度，后续仍应进一步确认：

- `/cloud_registered` 的原始 frame 语义
- bridge 重整 frame 后与 `map` 的一致性
- 长时间运行下 `map/odom/base` 语义是否持续稳定

## 五、下一步计划

下一步不再是继续证明"能不能打通"，而是进入"稳定、收敛、固化"的阶段。

### 第一优先级：稳定最小闭环

目标：

- 让已经跑通的导航闭环具备更好的重复性
- 降低偶发性和误判成功的概率

建议任务：

- 继续做 `0.6 m` 与 `1.0 m` 的往返测试
- 调整 `xy_goal_tolerance` 与 `yaw_goal_tolerance`
- 收敛速度参数，避免过激控制

### 第二优先级：固化测试流程

目标：

- 把当前人工联调经验固化成稳定测试方法

建议任务：

- 完善重复导航测试脚本
- 增加往返测试与结果记录能力
- 将测试过程形成标准文档和回归流程

### 第三优先级：提高导航工程完整性

目标：

- 让当前链路从"能跑"走向"更可维护、更可扩展"

建议任务：

- 进一步核对 frame 语义
- 优化地图生成参数
- 明确更长期的静态地图 / 在线地图使用边界

### 第四优先级：后续功能扩展

在最小闭环稳定之后，再进入更高层能力：

- 更远距离导航
- 更复杂环境导航
- 楼梯检测
- 多楼层任务管理
- 局部 3D 通行扩展

## 六、当前阶段结论

截至 2026 年 3 月 25 日，当前项目已经完成的不是单点功能验证，而是以下完整链路的一次真实贯通：

`FAST-LIVO2 -> fastlivo_nav_bridge -> floor_mapper -> Nav2 -> /cmd_vel_nav -> /cmd_vel -> robot motion`

因此，当前阶段可以明确下结论：

- 建图输入链已具备
- 路径规划链已具备
- 导航执行链已具备
- 最小全链路已打通并完成实际验证

当前后续工作的重点，应从"接线和打通"转向"稳定性、重复性和工程收敛"。
